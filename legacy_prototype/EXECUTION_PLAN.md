## Sprint 6 — Chat layout + Neural-Map quick fixes

**Goal:** the daily-driver screens stop being annoying.

### 6.1 Move the right-side "system controls" out of chat
- Today `finchat_chat.html` has a right panel with tabs **Proof / Tokens / Rules / AI Scans** (`.ptab` buttons ~line 552, `switchTab()` ~line 1795).
- Move all four tabs to **`finchat_audit.html`** as new sections (Audit already has the proof-chain mindset; "AI Scans" and "Proof" belong there naturally; "Tokens"/"Rules" become an "Economy" section).
- Chat page becomes two columns: **left = persona/agent list + channels**, **right = the conversation, full width**. Keep only the compact token pill in the topbar.
- Implementation note: extract the moved panels' JS into `frontend/system_panels.js` (shared-file pattern) so a design-tool regen of chat can't wipe it again.

### 6.2 Neural-map edge rendering — straight solid lines
- `finchat_neuralmap.html` ~line 743: `if (!e.derived) ctx.setLineDash([5/view.scale, 4/view.scale])` — this is why user-created connections render as broken/dashed lines.
- Fix: draw **all edges solid** by default. Preserve the derived/custom distinction some other way (slightly different opacity or the existing color difference), and add an optional per-edge `style` (`solid`/`dashed`) in `neural_map_edge_meta` for users who *want* dashed.
- "Straight line" also means: keep the current straight `lineTo` rendering (it is already straight, not curved) — the complaint is the dash pattern.

### 6.3 Fix the bottom-right legend ("data totally wrong")
- `renderLegend()` (~line 383) prints a **static list of all six node types** with colors, regardless of what the current map actually contains — on a custom map with 2 idea nodes it still shows Agent/Tool/On-chain/etc.
- Fix: compute live counts from the loaded graph (`nodes.filter(n => n.type === k).length`), show only types with count > 0, render as `● Agent × 6`. Re-render on every graph load/mutation and on map-tab switch.
- While in there, audit `#mapStats` (header) for the same staleness.

### 6.4 Node color customization
- Node panel (opens on node click) gains a color swatch row + custom color input.
- Persist per node in **`neural_map_node_meta`** (already keyed by namespaced node key + `map_id` — add a `color` column via migration `...016` or store in its existing JSON payload). Renderer: user color overrides `T.cat[type]` fill; legend unaffected (legend keys off type, not color).
- Works for derived *and* custom nodes (meta table already annotates any node).

**Tests:** `scripts/test_sprint6_ui_state.js` — edge style persistence, node color CRUD + cross-map isolation, legend-count endpoint math (compute counts server-side in `GET /api/neural-map` response `stats` so the test can assert them).
**Acceptance:** chat is two-pane; audit page hosts the four tabs; new connections render solid; legend counts match DB; node color survives reload and other users can't see/edit it.

## Sprint 7 — Autonomous agent missions + tool expansion  ⚠️ *the major issue*

**Goal:** agents work on a loop without being prompted: gather data, run recurring jobs, use real tools, and pause for human approval before anything irreversible.

### 7.1 Mission engine (the loop)
New concept: a **mission** = a standing goal an agent re-runs on a schedule.

- **Migration `...016_agent-missions.js`:** table `agent_missions` — `mission_id, user_id, agent_id, title, goal (text), cadence ('15m'|'1h'|'6h'|'daily'|cron), enabled, max_tokens_per_run, last_run_at, last_execution_id, next_run_at, consecutive_failures`.
- **`services/agents/MissionScheduler.js`:** on boot, registers one BullMQ **repeatable job per enabled mission** (exact pattern already proven by `processMorningBriefing` in `WorkerPool.js`). Job processor calls the agent's Cognitive Core with the mission goal, records the execution id, decrements budget, writes a notification on completion/failure. Back off + auto-disable after N consecutive failures.
- **Routes `routes/missions.js`:** CRUD `GET/POST/PUT/DELETE /api/missions`, `POST /api/missions/:id/run-now`, `GET /api/missions/:id/history` (joins `executions` for tokens/duration).
- **UI:** Agents page gets a "Missions" section per agent — create/enable/pause, cadence picker, budget, last result preview. (Shared-JS file: `frontend/missions_widget.js`.)
- **Safety rail:** every mission run goes through the existing Sentinel preCheck + token budget (`agent-token-budgets` migration `...007` already exists — enforce `max_tokens_per_run` there).

### 7.2 Human-in-the-loop for irreversible actions
- Reuse Sprint 2 Phase 5 wait-states: any tool marked `requires_approval: true` in its manifest causes the execution to enter `WAITING` and fire a notification ("Rasha wants to submit an application to X — Approve / Reject").
- New route: `POST /api/executions/:id/approve|reject`. UI: approval cards in the notifications drawer + Operations page.
- **This is mandatory for job applications and any future trading.** Draft-first, human-approves, then the agent proceeds.

### 7.3 New tools (`tools/`, registered in `ToolRegistry`, seeded via migration `...017`)
| Tool | For | What it does |
|---|---|---|
| `FetchTool` | all | fetch a URL → strip boilerplate (readability-style extraction) → clean text + metadata. The single biggest unlock for "extract data from different websites". |
| `CrawlTool` | nova | bounded same-site crawl (depth ≤ 2, ≤ 10 pages, robots.txt respected, per-domain rate limit) built on FetchTool. |
| `NewsTool` | aurelius, nova | crypto/finance headlines via free RSS/JSON feeds (CoinDesk, CoinTelegraph RSS; no key needed) with recency filter. |
| `ApplyDraftTool` | rasha | takes a job posting (from JobsTool/FetchTool) + resume (ResumeTool) → produces tailored cover letter + application package saved as a document; flags `requires_approval` for any actual submission step. |
| `WatchlistTool` | aurelius | CRUD a user's crypto/stock watchlist (new table in `...017`); missions read it to know what to track. |
- Existing `SearchTool` (DuckDuckGo HTML) stays the discovery entry point; FetchTool is the follow-through.
- **Remember:** update `agent_configs.tools` in the migration *and* call `refreshRegistry()`; keep the MANDATORY TOOL USE header pattern in `personas.js` for any agent getting new tools.

### 7.4 Flagship missions to ship as seeds (proof the loop works)
1. **Rasha — Job hunt (daily):** JobsTool + SearchTool + FetchTool → shortlist matching the resume → ApplyDraftTool per top match → notification with drafts awaiting approval. *Actual submission stays human-approved; unattended form-submission on third-party sites is deliberately out of scope (fragile + ToS risk).*
2. **Aurelius — Crypto brief (every 6h):** WatchlistTool + CryptoTool + NewsTool → price moves, relevant news, and an *educational* buy/sell/hold rationale per watched coin, with sources cited. **No real trading in this sprint.** If trading is ever added: paper-trading ledger first, then devnet, and every real order behind the 7.2 approval gate — plus a visible "not financial advice" disclaimer in the UI.
3. **Nova — Research digest (daily):** takes a standing research topic → SearchTool + CrawlTool + FetchTool → synthesized digest with links, stored as a document and pushed as a notification.

**Tests:** `test_sprint7_missions.js` (CRUD, scheduler registration/dedup, budget cutoff, failure backoff, approval-gate state transitions), `test_sprint7_tools.js` (each new tool against live endpoints; structural assertions, not wall-clock ones — Supabase latency flakes were already hit in Sprint 5).
**Acceptance:** with the server left running, each seeded mission fires on schedule, produces a visible artifact (message/document/notification) with real data and source URLs, spends tracked tokens, and anything irreversible waits for approval.

## Sprint 8 — Knowledge layer: documents & notes on nodes, time filter, activity stats

**Goal:** the Neural Map becomes an Obsidian-style knowledge base, not just a viewer.

### 8.1 Documents & notes inside nodes
- **Migration `...018_node-documents.js`:** `node_documents` — `doc_id, map_id, node_key (namespaced, same scheme as meta tables), user_id, kind ('note'|'file'|'reference'), title, content (markdown, for notes), file_path/mime/size (for uploads), url (for references), created_at, updated_at`.
- **Backend:** `multer` upload to `uploads/` (dir already exists at repo root) with size/type allowlist (pdf, md, txt, docx, png/jpg, ≤ 10 MB); routes `GET/POST/DELETE /api/neural-map/maps/:mapId/nodes/:nodeKey/documents`, download route with ownership check (same `requireOwnedMap()` guard pattern, 404 not 401).
- **UI (node panel):** new "Notes & Documents" tab on node click — markdown note editor (textarea + preview is enough; no heavy editor dependency), file upload, reference-URL adder, list with delete. Node renderer shows a small badge/dot when a node has attachments.
- Applies to **any** node (agents, tools, entities, custom) — the namespaced-key design already supports this.

### 8.2 Time-based filtering ("time packing")
- All map tables already have `created_at`. Add a **timeline control** to the map toolbar: presets (Today / 7d / 30d / This year / All) + a from–to range scrubber.
- Filter client-side (nodes+edges outside range fade to ~8% opacity rather than vanish, so context is preserved; toggle to fully hide). Derived system nodes (agents/tools) are always shown — they're infrastructure, not dated knowledge.
- `GET /api/neural-map` response gains per-node `created_at` where missing today.

### 8.3 Activity database & heatmap ("how much did I add per day")
- Endpoint `GET /api/neural-map/activity?days=365` — one grouped query over `neural_map_nodes` + `node_documents` + `neural_map_edges` counting creations per day per kind.
- UI: GitHub-style contribution heatmap + "last 7 days" list ("Yesterday: 3 notes, 1 document, 2 connections") in a collapsible map side panel; clicking a day applies the 8.2 time filter to that day.

**Tests:** `test_sprint8_documents.js` (doc CRUD, upload validation, cross-user 404, node-key scoping), `test_sprint8_activity.js` (seed dated rows → assert exact daily counts).
**Acceptance:** click node → add note/file/reference → badge appears → survives reload; timeline scrubber visibly filters; heatmap numbers match seeded data.

## Sprint 11 — Model Lab: from visual NN to real fine-tuning

**Goal:** evolve the Neural Network page from an educational MLP toy into a pipeline that produces an actually-usable fine-tuned model. (Long-term this may split into its own app — build it as a self-contained module so that split stays cheap.)

### Phase A — Dataset builder (no external dependency, immediate value)
- New "Datasets" tab on `finchat_neuralnetwork.html`: curate training examples from FinChat's own data — chat exchanges, mission outputs, documents (Sprint 8), memory entries. Select → clean → label → export **JSONL in chat-completions format**.
- Table `training_datasets` (migration `...019`); versioned, with train/val split and stats (examples, tokens).
- This is valuable even before any training happens (quality-controlled corpus of "how my agents should answer").

### Phase B — Fine-tuning backend (decision required)
Reality check: **Groq does not offer fine-tuning.** Realistic options, in recommended order:
1. **Local LoRA on the Ollama fallback path** (e.g., fine-tune a qwen2.5-class small model with a LoRA adapter, serve via Ollama `Modelfile`). Zero recurring cost, private, and plugs into the existing `inference.js` fallback; needs a capable GPU or patience.
2. **Hosted fine-tune (Together AI / Fireworks / OpenAI)** — upload the Phase A JSONL, poll job status, register the resulting model id as a selectable per-agent model in `runtime_settings` (selector UI already exists). Fastest path to "my agents run on my model."
- Build the abstraction either way: `services/ml/FineTuneManager.js` (submit job, poll, register model), `fine_tune_jobs` table, UI with job status + eval loss curve.

### Phase C — Evaluation & rollout
- Reuse the Phase A val split: side-by-side eval (base vs fine-tuned) on held-out prompts, scored by the judge pattern from DebateOrchestrator; one-click "assign model to agent" via the existing per-agent model selector; instant rollback.

### Visual NN builder (existing `nn_core.js` page)
- Keep as the **learning tool** it is; small additions only: save/load architectures as named experiments, and a clear UI note that this MLP sandbox and the fine-tuning pipeline are different tracks. Do not try to make the canvas MLP "become" the LLM fine-tuner — they are pedagogically related, not technically.

**Tests:** `test_sprint11_datasets.js` (curation CRUD, JSONL export format validity), `test_sprint11_finetune.js` (job lifecycle with a mocked/stub provider + one real smoke run).
**Acceptance:** export a real dataset from own chat history; complete one fine-tune job end-to-end; select the resulting model for an agent and see it answer.

## Sprint 12 — Next.js migration (old Sprint 5D) — do last

**Why still worth it:** the design-tool regen keeps wiping hand-wired JS on the three managed pages; a componentized app ends that class of bug permanently, and the static-HTML + shared-JS pattern is at its limits (chat page is ~2,200 lines of JS).

- Incremental strangler migration: Next.js app served alongside Express (proxy `/api/*`); migrate page-by-page in this order: Settings → Blockchain → Operations → Agents → Neural pages → Chat (hardest: sockets + optimistic sends + proof reconciliation) → retire static pages.
- Port the canvas engines (`neuralmap`, `nn_core.js`) as-is inside React wrappers — they are framework-agnostic already; do not rewrite them.
- Keep every existing test green throughout; the API contract does not change.

## Cross-cutting rules for every sprint

1. **Verify, don't trust reports.** Every sprint ends with its test script run for real and the actual pass count recorded (history: a "54/54" report was actually 53/54).
2. **Migrations are append-only** (`...016` onward), each with a working `down`.
3. **After any tool/seed change:** update `agent_configs.tools` *in the migration* and call `refreshRegistry()` — the Redis 5-min cache has silently masked seed changes before.
4. **No wall-clock assertions against Supabase** — assert structure/persisted state, not latency.
5. **Frontend logic goes in shared `.js` files**, not inline in the three design-tool-managed pages, until Sprint 12 lands.
6. **Approval gates are non-negotiable** for anything that leaves the system: job applications, trades, on-chain writes with real cost. Draft → notify → human approves → execute.
7. **Budget every autonomous loop** (`max_tokens_per_run` + Sentinel preCheck) so a runaway mission can't drain the Groq quota overnight.
